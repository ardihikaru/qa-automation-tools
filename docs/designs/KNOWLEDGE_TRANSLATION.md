# Knowledge translation (EN / ID) and draft write-back to the automation repo

Status: Draft. Author: ardihikaru (drafted by Claude). Components: ai-backend, dashboard. Date: 2026-11-27.
Depends on [PRODUCT_KNOWLEDGE_SYNC.md](PRODUCT_KNOWLEDGE_SYNC.md), [CASE_AUTOMATION.md](CASE_AUTOMATION.md), [AI_CONVERSATIONS.md](AI_CONVERSATIONS.md). Code references use function names; lines are as of `main` at `4895fc0`.

## Overview
The knowledge base (`kb_*`) is English, because the automation repo's `docs/` catalog is English. This spec adds (1) an Indonesian (ID) reading view, translated by an LLM and stored only in the DB, and (2) ID authoring of drafts, translated to English on save, plus an optional, human-triggered write-back of drafts to the repo as a pull request.

## Problem
1. Indonesian-speaking QA staff read and search an English catalog (scenarios, stories, features, modules).
2. Drafts (`origin='local'`, `L-…` codes, `SaveDraft` in `knowledge/query.go`) live only in the DB. They never reach the repo, so the repo, GAOS and the exports cannot see them.

## Goals
- ID text for: `kb_parts.name`, `kb_modules.name`, `kb_submodules.name`, `kb_features.name` + `notes`, `kb_epics.title` + `area`, `kb_stories.text`, `kb_test_cases.scenario`.
- Per-user language (`en|id`), a header toggle, fallback to English, a "machine translated" marker.
- Search (`q`) matches English and Indonesian text.
- Translation runs in the background after each sync, only for new or changed text. It never blocks or fails a sync.
- A draft written in ID is stored in English in the normal columns; the ID original is kept.
- Drafts can be published to the automation repo as a PR (English), never to the default branch.

## Non-Goals
Translating the dashboard chrome (labels, buttons); other languages; translating annotations, notes, job logs or AI summaries; changing the repo or what a sync writes to `kb_*`; changing exports and the GAOS push (they keep reading English `kb_*`).

## Decisions
- **Model.** `ChatOpts` gains `Model string`. `aiManagerProvider.Chat` sends `opts.Model` when set, else `p.cfg.Model` (`ai/aimanager.go`, request built around line 102). Provider stays `claude-v3` with `no_fallback`, and the existing pin check still applies. No new upstream, no direct call to `:8105`, and no change to ai-manager or ai-claude-cli: verified live on the claude-v3 worker that `claude --model claude-haiku-5-5` works (alias `haiku` resolves to the same; about $0.0014 per tiny call), ai-manager has no model allow-list for claude-v3, and ai-claude-cli passes `model` straight to the CLI. New env `AI_TRANSLATION_MODEL=claude-haiku-5-5` (explicit id, not the alias; empty disables translation). ai-manager echoes the *requested* model in `ChatResult.Model`, so that field proves nothing: the first translation run logs a warning when the reply model differs from the request (a startup/first-run assertion, never an error), and the tokens and cost are stored as the CLI reported them (`kb_translation_runs`, `ai_call_log`, `ai_conversations`).
- **Storage.** New `kb_translations`, never touched by `store.go` `apply`, so a sync cannot overwrite it and the English columns are unchanged. The key is `(product_id, entity_type, code, field, lang)`: the requested `(product_id, entity_type, code, lang)` plus `field`, because features, epics and others have two text fields, and per-field staleness avoids re-translating a scenario when only its status changed. Staleness is `src_hash` (SHA-256 of the trimmed, NFC-normalised English field text) versus the current text; the row `content_hash` is not used because it also covers status, level and links.
- **Language.** `users.language` (`en|id`, default `en`). `?lang=en|id` overrides it per request. Impersonation reads the effective user.
- **Read shape (additive).** Existing English fields never change. When the effective language is `id`, items gain `i18n: { lang, fields: { <field>: { text, state } } }`, `state` in `machine | original | stale`. The dashboard shows `i18n` text when present, else English, with the marker for `machine` and `stale`. A stale text is still shown (and searched) until re-translated.
- **Search.** `q` stays English-or-ID regardless of the display language: each `LIKE` gets `OR EXISTS (SELECT 1 FROM kb_translations x WHERE x.product_id = t.product_id AND x.entity_type = ? AND x.code = t.code AND x.lang = 'id' AND x.text LIKE ?)`. Existing `q` is in `Stories` (`query.go`), `TestCases` (`query.go`) and features (`coverage.go`). `Epics` and modules get a new `q` (code + title/area, code + name).
- **Translator** (new `knowledge/translate.go`): a `Translator` built beside the `Syncer`, started from `Syncer.OnSucceeded` (the hook documented in `knowledge/README.md`; panics are recovered by `notify`). It selects fields with no `lang='id'` row or a stale `src_hash` among active rows, batches up to 20 fields (or 6,000 characters) per call as JSON `{id, text}` in and out, and writes the rows in one transaction per batch. Backfill is the same code path on first run (nothing exists yet), plus `POST …/translations/run` to force it. One run per product at a time, at most 2 products in parallel (`TRANSLATE_CONCURRENCY`, default 1). Calls use `Feature: "knowledge-translation"`, temperature 0.1, and a new conversation kind `translation` (one conversation per run, `Ref` = run id; `ai_conversations.kind` is `VARCHAR(8)` in `migrations.go`, too short for it, so the kind is widened to `VARCHAR(16)` and `ai/conversation.go` gets `ConvTranslation`; the same kind covers draft ID to EN calls).
- **Prompt and validation.** The repo text is not guaranteed English (some columns are already Indonesian). The model returns JSON `{id, source_lang: "en"|"id"|"mixed", text}` per field. `en`: text is the Indonesian translation (`state='machine'`). `id`: text is the source unchanged (`state='original'`, no machine-translated marker). `mixed`: only the English portions are translated. The English columns are never rewritten (sync owns them). Keep in English inside the Indonesian text: Given / When / Then, UI element, button and menu labels, field names, codes (`TC-…`, `US-…`, `A01.07`), URLs, identifiers and anything code-formatted; translate only the prose around them (prompt rule). Validator: a batch is rejected if the JSON is invalid, ids differ, a field is empty, or any code token, backtick span, `{placeholder}`, URL or Given/When/Then keyword of the source is missing from the output. The batch is then split in halves and retried once; single items that still fail go to `kb_translation_failures` (attempts, `next_try_at` with backoff 1 h, 6 h, 24 h, give up at 5, `last_error` clipped like `ai_error` in `sync.go`). The next run retries due failures. The first rollout backfills one product and a native speaker reviews the batch before the others.
- **Draft in ID.** The draft body gains `lang` (`en|id`, a hint only). `SaveDraft` first sends the text fields (`scenario`, `text`) through the same model (synchronous, `AI_TIMEOUT_SECONDS`) with an ID-to-EN prompt returning `{source_lang, text}`. Only when `source_lang` is `id` or `mixed` is the English result stored in `kb_test_cases` / `kb_stories` and the typed text kept in `kb_translations` (`state='original'`); when it is `en` the text is stored as typed and the ID view is produced later by the normal translator. A failure returns 502 and saves nothing (the form keeps the text). Editing a draft in English marks its ID original stale; the translator then replaces it with a machine text. A machine run never overwrites a fresh `original`.
- **Write-back, recommended: human-triggered, PR only.** Automatic publishing is rejected: drafts are unreviewed and a repo PR is hard to retract. A "Publish drafts" button (roles with `canWrite`) opens one PR per epic on the automation repo. Details below.

## Write-back design
Reads today (`testcatalog.go`): `ReadTree` of the bare mirror on the default branch, parsed by `testCatalog.Parse` (`testcatalog.go`): an epic is one `.md` under `docs/test-catalog/`, stories are `- **US-X-NN** ([A01.07](…)) — text` bullets under `## User stories`, cases are 10-cell rows `| ☐ | TC-X-NNN | US-X-NN | scenario | + | API | P1 | planned | | |` (cells split on `|`, no escaping, `cells()`). Writes reuse the case-automation git path.
1. **Guard.** Only the product's automation repo is ever a target (`loadAutomationRepo`, `api/case_automation.go`). Before each step call `repoWriteAllowed` with `RepoOpCreateBranch`, `RepoOpPush`, `RepoOpOpenPR` (`api/product_repos.go`), which honours `allow_non_automation_work` and the automation role. Otherwise 403 `ErrWriteNotAllowed`.
2. **Preconditions.** No running sync; the product's latest succeeded sync commit equals the default branch head after `FetchOrigin`, else 409 "sync first". Drafts that are `origin='local'`, have English text, and are not in an open publication. A draft case whose story is also a draft is published with that story or not at all.
3. **Branch.** `qa-auto/kb-<epic>-<UTC yyyymmddhhmm>` (the `qa-auto/` prefix is enforced by `Pool.Push` and `Pool.OpenPR`); `Pool.AddWorktree` from the default branch, exactly like `poolRepo.Prepare`. The default branch is never pushed, and push is never forced (`worktree.go`).
4. **Codes.** Repo codes are assigned here: next free `TC-<E>-NNN` / `US-<E>-NN`, where `<E>` is `kb_epics.code` (Open question 2), and NNN is the maximum over the worktree file, all `kb_*` rows (removed included) and non-failed `kb_publications`, plus one.
5. **Render** (new `knowledge/publish_render.go`, pure): append story bullets after the last bullet of `## User stories` (links to the feature part files, relative to the epic file) and case rows after the last row of the table, in English, with `Done` = ☐ and the draft's status. Cell text is escaped by the grammar below. The only refusal is text the grammar cannot represent (a control character other than tab, LF, CR, or a literal `<br>` tag), with a clear error naming the field.
6. **Round-trip gate.** Before commit, run `testCatalog.Parse` over the worktree's files: it must add no new Problem, and the new stories and cases must equal the drafts field by field (after the canonical form below). Otherwise abort and remove the worktree.
7. **Job.** "Publish drafts" enqueues a `drafts_publish` job in `job_runs`, one per epic, serialized per product (one queued or running publish per product, else 409), with a `job_events` live log on the existing `/jobs/:id` page, the same machinery as `case_create` / `policy_propose` (`api/jobs_resume.go` restarts orphans; the type is added there with a safe restart that reuses the open branch). The job runs steps 2 to 6, then `Pool.Commit` (the one epic file), `Pool.Push`, `Pool.OpenPR`; the PR body lists local to repo codes and the author. It records state in `kb_publications` (`queued | running | pr_open | merged | failed`, `pr_url`, `branch`, `epic_code`, the codes mapping, `job_id`). The knowledge page polls it and shows a "Publishing… / PR open / Merged / Failed" badge on each draft. A draft in an active publication is read-only (edit and delete return 409).
8. **Reconcile** inside `OnSucceeded` before translation is queued, with `Pool.PRStatus` (`repopool/prstatus.go`, read-only). PR merged and the repo code now exists as `origin='sync'`: in one transaction, re-key `kb_case_results`, `kb_case_verifications` (and `kb_case_verification_events`), `kb_annotations` and `kb_translations` from the `L-` code to the repo code (an `original` ID text whose English hash no longer matches, because a reviewer edited the PR, becomes stale), mark the publication `merged`, and hard-delete the `L-` draft (as `DeleteDraft` does). `job_runs` payloads and `case_approvals` keep the `L-` code as history; the `kb_publications` mapping lets the API resolve `L-…` to the new code and the job page show "was L-…". PR closed without merge: publication `failed` with the reason, the draft is publishable again, the reserved code is released.
Round-trip safety: `L-` codes can never collide with repo `TC-`/`US-` codes, so `store.go` (`exists as a local draft; repo entry ignored`) is never triggered and no Problem is raised; a repo entry is simply a new sync row. Two PRs racing for the same NNN conflict at merge; the second is closed and republished with fresh codes.

## Catalog cell grammar (parser change, first PR after this spec)
Today `cells()` (`testcatalog.go`) is `line.split('|')`: no escaping, and a row is one line. No file under `testdata/` contains `\|` or `<br>`, and per the maintainer the existing catalog rows contain none either. The change is backward compatible for every row that has neither `\|` nor `<br>`:
- **Pipe.** A run of k backslashes immediately before `|`: k odd means a literal `|` preceded by (k-1)/2 backslashes; k even means a cell delimiter and the run is kept unchanged. A backslash anywhere else is literal, so `\d`, Windows paths and the like parse as before. The writer emits 2m+1 backslashes for a literal `|` that follows m literal backslashes, and always writes ` | ` with spaces, so a trailing backslash never touches a delimiter.
- **Newline.** `<br>`, `<br/>` and `<br />` (any case) decode to `\n` in cell text and in story text; the writer emits `<br>` for LF (CR dropped). A literal `<br>` tag in a draft is refused (it would decode to a newline).
- **Canonical form.** Cells are trimmed (`cells()` already does), so leading and trailing whitespace of a field is not significant: `parse(write(x)) == canon(x)`, `canon` = CRLF to LF, trim each end.
- Raise `testCatalog.Version()` to 4 so `parserVersion` (`sync.go`) re-parses; existing rows contain no `<br>`, so decoding is backward compatible and nothing changes for them; the checklist exports print a newline for a `<br>` (accepted). Rows that had `\|` were already mis-split into extra columns (a Problem today).

## Schema (appended to `migrations.go`, idempotent, skip-if pattern as `knowledge_format`)
- `ALTER TABLE users ADD COLUMN language ENUM('en','id') NOT NULL DEFAULT 'en'`.
- `kb_translations(product_id INT, entity_type ENUM('part','module','submodule','feature','epic','story','test_case'), code VARCHAR(64) utf8mb4_bin, field VARCHAR(20), lang CHAR(2), text TEXT, src_hash CHAR(64), source_lang ENUM('en','id','mixed'), state ENUM('machine','original'), model VARCHAR(64), translated_at DATETIME, PRIMARY KEY (product_id, entity_type, code, field, lang), FK product_id ON DELETE CASCADE)`. Search uses the PK prefix plus `LIKE` (a scan per product, like the current `LIKE` on `kb_*`).
- `kb_translation_runs(id BIGINT AI, product_id, trigger_kind ENUM('sync','manual','draft'), status ENUM('running','succeeded','failed'), total, done, failed INT, input_tokens, output_tokens INT, cost_usd DECIMAL(10,4), started_at, finished_at, error VARCHAR(400))`.
- `kb_translation_failures(product_id, entity_type, code, field, attempts TINYINT, next_try_at DATETIME, last_error VARCHAR(400), PRIMARY KEY (product_id, entity_type, code, field))`.
- `kb_publications(id BIGINT AI, product_id, job_id, entity_type ENUM('story','test_case'), local_code, repo_code, epic_code, branch, pr_url, state ENUM('queued','running','pr_open','merged','failed'), error VARCHAR(400), created_by CHAR(36), created_at, updated_at, INDEX (product_id, entity_type, local_code))`; `kb_translation_runs` startup cleanup mirrors `FailOrphanedSyncs`.
- `ALTER TABLE ai_conversations MODIFY kind VARCHAR(16) NOT NULL` (idempotent).

## API
- `GET /api/auth/me` gains `language`; `PUT /api/auth/language` `{language}`.
- Knowledge list and detail routes accept `?lang=`; items gain `i18n` (above). `q` as above.
- `GET /api/products/{id}/knowledge/translations/status` (any reader) returns `{enabled, model, lang_coverage: {total, translated, stale, missing, failed}, running, last_run}`. `POST …/translations/run` (`canWrite`) forces a run, 409 while running, 503 when `AI_TRANSLATION_MODEL` is empty.
- Draft `POST` / `PUT` bodies gain `lang` (hint). `kb_translation` items carry `source_lang`. Story and case text read from the repo may now contain `\n` (from `<br>`).
- `GET …/knowledge/publish/preview` returns drafts grouped by epic with the planned codes and blockers. `POST …/knowledge/publish` `{epic_code}` (`canWrite`) returns `{publications, pr_url}`, 409 / 403 / 422 for the failures above. It returns the new `job_id` (202); state is in `kb_publications`, polled by the dashboard, and the log is the job page. Drafts, stories and cases gain `publication: {state, pr_url, repo_code, job_id} | null`.

## Failure modes
| Failure | Behaviour |
|---|---|
| ai-manager down, model rejected, rate limit | Run `failed`, rows go to `kb_translation_failures`; sync already committed; English shown. |
| Reply broken or drops a code | Split, retry once, then a failure row. |
| Source edited mid-run | `src_hash` mismatch at write: row not written. |
| Draft translation fails | 502, nothing saved. |
| Draft text with a control character or a literal `<br>` tag | 422 at publish with the field named; the draft stays unpublished. |
| Model replies with a different model than requested | Warning logged once per run; translation continues. |
| Push or PR fails after the branch exists | Job and publication `failed`; worktree removed; a retry creates a fresh branch. |
| PR reviewer edits text | Reconcile marks the ID original stale. |
| Server restart mid-run | Orphan runs failed at startup; the next sync or manual run resumes by the pending query. |

## Cost and limits
Roughly 2.5k catalog fields on a catalog like the reference one (about 1.7k cases, 250 stories, 450 features), so about 130 calls at 20 per batch for a backfill; steady state is a handful of calls per sync. The real figure is unmeasured: the first backfill reports tokens and cost in `kb_translation_runs` and `/cost`. Limits: batch 20, concurrency 1 (max 2), temperature 0.1, 1 s pause between calls, nothing translated while `AI_TRANSLATION_MODEL` is empty. Catalog text is sent to claude-v3 (as sync summaries already do).
