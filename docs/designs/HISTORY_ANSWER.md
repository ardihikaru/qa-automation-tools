# HISTORY_ANSWER: answer a waiting approval from `/history`, relayed to GAOS, with its source recorded

*   **Author:** ardihikaru (drafted by Claude)
*   **Status:** Rev 2, **implemented** (2026-11-21) after one EGM review round (implementation readiness, design, codebase details); section 13 resolves the findings and supersedes earlier wording. The product owner asked for it; operator approval is delegated to the orchestrating agent under the product owner's standing instruction (recorded here, section 12).
*   **Depends on:** [CASE_AUTOMATION.md](CASE_AUTOMATION.md) (the approval gate, `case_approvals`, `POST /api/jobs/{id}/approval`, the GAOS Inbox item), [LEARNING_LOOP.md](LEARNING_LOOP.md) (`policy_propose` reuses the gate), [RUN_HISTORY.md](RUN_HISTORY.md) (the `/history` page and `GET /api/history/builds`), [GAOS_INTEGRATION.md](GAOS_INTEGRATION.md) (the GAOS client, `GAOS_API_URL`, `GAOS_API_TOKEN`).

## 1. Problem

The product owner: "If there is something waiting for approval in the QA tool, add a button on the `/history` page as a shortcut to answer, and send the answer to GAOS. We need a REST API in GAOS so they can communicate properly. In GAOS, log which source the answer came from: GAOS itself, the QA tool (with its domain), or another source (future: Hikaru app, Android Hikaru app)."

What exists today:

*   **The gate.** `caseauto.AwaitApproval` (`ai-backend/internal/services/caseauto/approval.go`) opens one `case_approvals` row per round (`external_id` = `qa-<jobId>-pr`, `-pr2`, …), creates a GAOS Inbox item when the job's product is GAOS-integrated (`gaos_created = 1` on success), then polls the row every 2 s and GAOS every 30 s. The first answer wins (`ApprovalStore.Answer` updates only `WHERE status = 'open'`). Used by `case_create` (`machine.go` `approve`) and `policy_propose` (`learnloop/proposer.go` `await`). Both send the same three options in the same order: **1 Approve, 2 Reject, 3 Needs changes**.
*   **Three doors write an answer.** The job page (`POST /api/jobs/{id}/approval`, roles Admin/DevOps/Developer/QA/QC via `productRole`'s `canVerify`; `answered_by = 'dashboard'`), the GAOS webhook (`POST /api/v1/gaos/inbox-answer`, `answered_by = 'gaos'`) and the GAOS poll inside `AwaitApproval` (`answered_by = 'gaos'`); expiry writes `'system'`.
*   **Who answered is not recorded.** `answered_by` (`VARCHAR(16)`) holds only the door. The username of a dashboard answer exists only in a job event text ("answered in the dashboard by ardi: approve"). GAOS does not tell us who answered there.
*   **A dashboard answer never reaches GAOS.** The GAOS item stays open until it expires (72 h), showing a question that was already answered.
*   **`/history`** lists builds (`case_create`, `case_run`) read-only. A `policy_propose` job is not a build and is not listed there.

## 2. Goal and non-goals

Goal:

1.  `/history` shows every approval that is waiting now (any job type that uses the gate), with an **Answer** button that opens a dialog with the same three options as the GAOS item and enough context to decide.
2.  Submitting relays the answer to GAOS through a new GAOS endpoint when the item exists in GAOS, so GAOS closes its item and logs the source; the job continues at once. When GAOS cannot take it, the answer is applied locally (today's behaviour).
3.  The QA side records where every answer came from (`gaos`, `qa-tool:history`, `qa-tool:job-page`, `system`), who gave it, and GAOS's own source object when GAOS sent one; the job page and `/history` show "answered via … by …".

Non-goals: any change to what the QA tools push to GAOS (the D-077 catalog/results contract); a new job type; changing the job page's door (it stays local-only, see 11.1); a durable retry queue for the relay (3.6); notifications; building the GAOS side (another agent implements the fixed contract in section 5).

## 3. Decisions

1.  **One write route, two doors.** The shortcut uses the existing `POST /api/jobs/{id}/approval` with a new optional field `"via": "history" | "job-page"` (default `job-page`) and an optional `"external_id"`. Same role check, same validation, same "first answer wins". A second route would duplicate the validation; a POST under `/api/history/` would break RUN_HISTORY's "history routes are GET-only".
2.  **`external_id` pins the round.** When present it must equal the job's latest approval's external id, else 409 `{"error": "a newer approval round exists", "status"}`: the dialog was opened on round 1 and the machine has since opened round 2, so the human has not seen what they would be approving.
3.  **Only `via: history` relays to GAOS.** Relay conditions, all required: `via = history`; the approval is `open` locally; `gaos_created = 1`; `r.gaos.Configured()`; and the approval's product currently has `gaos_integrated = 1` with a valid `gaos_product_id`. Otherwise the answer is local (path b).
4.  **Path (a), relay.** `gaossync.AnswerInboxItem(ctx, gaosPID, externalID, InboxAnswer{Choice, Text, Actor})` with a 15 s budget (one request, no retry). Outcomes:
    *   **200**: the returned `optionLabel`/`choice` are mapped with `DecisionFromAnswer`; the local row is answered with source `qa-tool:history`, the actor, and GAOS's returned `source` as detail. If the row was already closed by GAOS's webhook in the meantime (the webhook can arrive before GAOS answers our call), the row is **claimed**: `UPDATE … SET answer_source = 'qa-tool:history', answer_actor = ? WHERE external_id = ? AND status = ? AND answer_source = 'gaos'` — truthful, because GAOS's 200 says our call is the answer. The user gets 200.
    *   **409 `already_answered`**: someone answered first in GAOS. Its body's answer is applied locally through the webhook's code path (source `gaos`, GAOS's actor and source object). The user gets 409 `{"error": "already answered in GAOS", "status", "answered_by_actor", "source"}` and the dialog says so. If the body cannot be mapped, the local row is left for the webhook/poll and the user still gets 409.
    *   **Anything else** (410 expired, 404 unknown item or an older GAOS without the route, 405, 401/403, 422, 429, 5xx, timeout, transport error, unreadable body): **path (b)**, the local answer, with a note. The note is shown to the user ("GAOS did not take the answer (…); it was applied in the QA tools only") and written as a job event. 404 on the route itself and 404 on an unknown item are not told apart: both mean "GAOS cannot take this answer", and both fall back the same way.
5.  **Path (b), local.** Exactly today's `store.Answer`, with source `qa-tool:history` (or `qa-tool:job-page`) and the actor. When a GAOS item exists, it is left to be answered there (ignored, first answer wins) or to expire.
6.  **No durable retry of a failed relay.** The answer that matters (the local one) is already applied and the job has moved on; the only loss is that the GAOS item stays open until it expires (72 h) or someone answers it there (a no-op on our side). That is today's behaviour for every job-page answer. A durable marker (the `gaossync` outbox pattern) would add a table column, a sweeper and a second relay path for a cosmetic gain; it can be added later without a contract change.
7.  **Choice mapping.** `approve → 1`, `reject → 2`, `changes → 3` (the option order of both callers of `AwaitApproval`). The relay sends the comment as `text` for every choice (GAOS stores it; "Needs changes" requires it, which the QA side already enforces). The relay never sends `n+1` ("own words").
8.  **Actor and impersonation.** `actor.username` = the effective user's username (the impersonated target when impersonating), clipped to 64. `actor.display` = `"<real username> as <target username>"` when impersonating (e.g. `ai-service as ardi`), else the user's full name, else omitted. The QA side stores the same string in `answer_actor` (`ardi`, or `ai-service as ardi`). Impersonated writes are already audit-logged by the auth middleware.
9.  **Source vocabulary (QA side), closed:** `gaos` (webhook, poll, or a 409 that carried someone else's answer), `qa-tool:history`, `qa-tool:job-page`, `system` (expiry). `answered_by` keeps its door value (`dashboard`, `gaos`, `system`) for compatibility; old rows have no source and are shown from `answered_by` (`dashboard` → "QA tools", `gaos` → "GAOS").
10. **GAOS's source object is stored verbatim** (JSON, ≤ 2 KiB, else dropped) from the 200/409 body, the webhook body (if GAOS adds `source` there; unknown fields are already tolerated) and the poll (`GET …/inbox/{externalId}` gains `source`). The actor shown for a `gaos` answer is `source.actor` when it is a string, else `source.actor.display`, else `source.actor.username`, clipped to 120.
11. **Who may answer** is unchanged: `productRole(req)`'s `canVerify` (Admin, DevOps, Developer, QA, QC). The list endpoint returns `can_answer` for the caller so the page hides the button for other roles; the POST still enforces it.

## 4. Data (`migrations.go`, appended, idempotent)

```sql
-- skip-if: SELECT COUNT(*) FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'case_approvals' AND column_name = 'answer_source'
ALTER TABLE case_approvals
  ADD COLUMN answer_source VARCHAR(32) NULL,
  ADD COLUMN answer_actor VARCHAR(120) NULL,
  ADD COLUMN answer_source_detail JSON NULL;
```

One ALTER, so it is atomic; the guard tests its first column. The old binary never names the columns (rollback-safe). `ApprovalStore.Answer` keeps its signature (the `Approvals` interface and its test fakes are unchanged) and derives the source from the door (`dashboard` → `qa-tool:job-page`, `gaos` → `gaos`, `system` → `system`); a new `ApprovalStore.AnswerSourced(ctx, ext, status, Answer{By, Text, Source, Actor, Detail})` writes all fields. `AwaitApproval`'s poll uses `AnswerSourced` when its `Approvals` implements it (an optional interface; fakes fall back to `Answer`). `Approval` gains `Source`, `Actor`, `AnsweredAt`; `approvalCols` reads them.

## 5. The GAOS contract (fixed; implemented by GAOS)

`POST {GAOS_API_URL}/products/{pid}/inbox/{externalId}/answer`, `Authorization: Bearer <GAOS_API_TOKEN>`, body

```json
{"choice": 1, "text": "optional", "actor": {"username": "ardi", "display": "ai-service as ardi"}}
```

`choice` is the 1-based option index (n+1 = own words; not used by the QA side). Responses: 200 `{"externalId", "status": "answered", "choice", "optionLabel", "text", "answeredAt", "source": {"kind", "client", "origin", "actor"}}`; 409 `{"error": "already_answered", …the same fields of the current answer}`; 410 expired; 404 unknown; 422 bad choice; 401/403. `GET …/inbox/{externalId}` gains `"source"`. GAOS derives `client` and `origin` (the QA tool and its domain) from the token; the QA side sends no origin of its own.

Client (`gaossync/inbox.go`): `AnswerInboxItem(ctx, gaosPID, externalID string, a InboxAnswer) (*InboxAnswerResult, error)`; `InboxAnswerResult{Item InboxItem; Already bool}` (Already = the 409). Same guards as the other Inbox calls (`inboxReady`), no redirects, notes without URL or body. Any other status is a `*Failure{Status, Note}`; 404 adds "(unknown item, or GAOS has no answer endpoint yet)". `InboxItem` gains `Source json.RawMessage`.

## 6. Routes (QA side)

*   `GET /api/history/approvals?product=` (every signed-in user, like the other history reads) → `{"items": [Waiting], "can_answer": bool}`, all open approvals, oldest first, capped at 200. `Waiting` = `{external_id, round, job_id, job_type, job_status, product_id, product_name, case_code, title, spec_path, report: {passed, failed, skipped} | null, gaos_created, relay: bool, created_at, waiting_ms}`. `title` is the policy draft's title for `policy_propose`, else "". `round` = 1 for `-pr`, N for `-prN`. `relay` = the relay conditions of 3.3 other than `via` hold now (so the dialog can say "will also be sent to GAOS"). Read from `case_approvals` (`status = 'open'`) and `job_runs` by `id IN (…)` (collations, RUN_HISTORY 11.1).
*   `GET /api/history/builds` gains `approval=open` (builds whose job has an open approval) and, per build, `"approval": null | {external_id, status, source, actor, answered_at, gaos_created}` (the latest round).
*   `POST /api/jobs/{id}/approval` body `{decision, text?, via?, external_id?}` → 200 `{"status", "via": "gaos" | "local", "note"?}`; 409 as in 3.2/3.4; existing 400/403/404/503 unchanged.
*   `GET /api/jobs/{id}/events`'s `approval` object gains `source`, `actor`, `answered_at`.

## 7. Dashboard

*   **`/history`**: a "Waiting for approval (N)" panel above the tabs, shown when N > 0, one row per waiting approval: job link, type ("Build" / "Policy proposal"), product, case link or policy title, spec path, last run counts, waiting since, "also in GAOS" badge, and an **Answer** button when `can_answer`. A Builds-tab filter "Approval: waiting" (`approval=open`), and per build row an Answer button when its latest approval is open; the expanded row shows "Approval answered via <source> by <actor>".
*   **Answer dialog** (`components/Modal.tsx`): the context above plus links to the job page (spec and diff are shown there); three choices (Approve / Reject / Needs changes) as radio buttons; a comment box (required for Needs changes, ≤ 1000); a line saying where the answer goes ("Sent to GAOS and applied here" or "Applied in the QA tools"). On 200 it shows the outcome and the note (fallback), refreshes the panel and the list; on 409 it shows who answered first.
*   **Job page** approval card: "Answered via GAOS by …" / "via the QA tools (history) by …" / "via the QA tools (job page) by …" / "expired".

## 8. Security

No new secret or allow-list path. The relay sends the token only to `GAOS_API_URL` (existing client: no redirects, no proxy). The comment is redacted (`r.caseAuto.redact`) before it is stored or sent, as today. GAOS's source object is stored size-capped and shown as text, never as HTML. The role check is the existing one.

## 11. Alternatives weighed

1.  **Relay from the job page too.** Same code, one flag. Left out: the owner asked for the history shortcut, and the job page's answer staying local keeps its latency and behaviour unchanged. Turning it on later is `via: "job-page"` taking the relay branch.
2.  **A durable relay queue.** Rejected for now (3.6).
3.  **Let GAOS's webhook be the only writer after a relay** (no local apply). Rejected: the job would wait up to 30 s (poll) or on webhook delivery; the brief asks for the job to continue at once.
4.  **Store the source in `answered_by`.** Rejected: 16 characters, and the learning loop and PR bodies read it as the door.

## 13. Review round 1 resolutions (supersede earlier wording)

Reviewers: `egm-implementation-readiness`, `egm-design`, `egm-codebase-details` (zero context). Rejected: "the GAOS client has no proxy-free transport" — `gaossync.New` sets `s.cl.hc.Transport = noProxyTransport()` (`sync.go`), so section 8 stands.

1.  **Relay call.** `(*Syncer).AnswerInboxItem` calls `c.once` directly: one request, no 429 loop, its own notes. It decodes the body on **200 and 409** into `InboxItem` (which gains `Source json.RawMessage`) and requires `externalId` to match (else a `*Failure`, "unexpected body"). Path segments are `url.PathEscape`d after `inboxReady`. 404's note is "GAOS does not know this item, or has no answer endpoint yet". The caller's budget is `context.WithTimeout(context.WithoutCancel(req.Context()), 15 s)`: a closed browser tab does not cut the call in half.
2.  **What the 200 means.** The **submitted decision** is applied locally (GAOS's 200 says it took our choice); if GAOS's `optionLabel`/`choice` maps to something else or nothing, a server log line records the mismatch. `AnswerSourced` then either changes the row (done) or not. When not: re-read the row. (i) `status` = ours and `answer_source = 'gaos'` (GAOS's webhook or poll landed first): **claim** it — `UPDATE case_approvals SET answer_source = 'qa-tool:history', answer_actor = ?, answer_source_detail = ? WHERE external_id = ? AND status = ? AND answer_source = 'gaos'`, and when it changes one row write the event "the GAOS answer above came from /history by <actor> (relayed)". (ii) Anything else (the job page, the learning page, or expiry closed it during the relay): 409 `{"error": "answered in the QA tools first", "code": "answered_here", status, source, actor}` and a **warn** job event "GAOS recorded <ours> from /history, but the QA tools had already applied <theirs> via <source>; GAOS shows a different answer". The machine reads `AwaitApproval`'s result once; a claim that lands after the machine read the row only changes the record and the event log, not the PR body (accepted: the PR body then says "GAOS", which is where the answer was relayed through).
3.  **409 from GAOS.** Body mapped with `DecisionFromAnswer`. If its `source.actor` (string, or `.username`) equals our actor username and the decision equals ours, it is our own earlier relay (a double submit across tabs): treated as 200. Otherwise, when it maps, it is applied with `applyGaosAnswer` (below), source `gaos`, and the user gets 409 `{"code": "answered_in_gaos", status, actor, source}`. When it does not map (an own-words answer the gate cannot use), **path (b)**: our answer is applied locally with the note "GAOS was answered in own words; your answer was applied in the QA tools".
4.  **Unknown outcome.** On a timeout or transport error (status 0) only, one `GetInboxItem` (5 s, same detached context) reconciles: `answered` and mapping to ours → 200 path; `answered` and mapping to another decision → 409 path; anything else → path (b) with the note "GAOS did not answer in time; the outcome there is unknown".
5.  **Fallback notes and logs.** Path (b) after a relay attempt writes a warn event and returns `{"status", "delivered": "local", "note"}`. 401/403/422 are logged at error level ("configuration error": token or choice mapping) — the user still gets the local answer.
6.  **Double submit.** An in-process lock per `external_id` (`sync.Map` of `*sync.Mutex`, `TryLock`): a second request while one is in flight gets 409 `{"code": "in_flight"}`. The dialog disables its buttons while sending. No circuit breaker: approvals are a handful per day; a down GAOS costs one 15 s wait per answer, and the dialog says it is waiting for GAOS.
7.  **Names.** `caseauto.AnswerMeta{By, Text, Source, Actor string; Detail json.RawMessage}`; `caseauto.SourcedAnswerer interface{ AnswerSourced(ctx context.Context, externalID, status string, m AnswerMeta) (bool, error) }`, implemented by `*ApprovalStore`; `AwaitApproval`'s GAOS poll uses it when `d.Approvals` implements it. `Approval` gains `Source, Actor string; AnsweredAt *time.Time` (scanned via `sql.NullTime`). `Approval.Who()` returns "<actor> (<source label>)" or the old `AnsweredBy`. `api.applyGaosAnswer(ctx, ext, jobID, status, text string, detail json.RawMessage, how string) (changed bool, current string, err error)` is extracted from `gaosInboxAnswer` (redact, clip, `AnswerSourced` with source `gaos` and the actor from `detail`, the event) and used by the webhook and the 409 path.
8.  **Source mapping, closed.** `qa-tool:history`, `qa-tool:job-page`, `qa-tool:learning` (the learning page's approve buttons, `views/learning/api.ts` `answerProposal`, send `via: "learning"`), `gaos`, `system`. **Any `expired` status is source `system`** whatever the door (GAOS-side expiry keeps `answered_by = 'gaos'`). `learning_loop.go`'s raw expiry `UPDATE` also sets `answer_source = 'system'`. `ApprovalStore.Answer` (kept for the interface and the fakes) derives: `dashboard` → `qa-tool:job-page`, `gaos` → `gaos`, `system`/expired → `system`.
9.  **Detail and actor hygiene.** `detail` is stored only when it is a JSON **object** of ≤ 2048 bytes, else NULL, checked before the `UPDATE` so it can never fail the status write. Actor strings: control characters removed, clipped by runes (`answer_actor` 120; `actor.username` 64; `actor.display` 120). The UI renders the source label from our column and the actor in a separate element; GAOS's free text is never used as the label.
10. **Request fields.** `approvalBody` gains `Via` (JSON `via`: `""`/`job-page`, `history`, `learning`; else 400) and `ExternalID` (JSON `external_id`), **required when `via = history`** (400 when missing). The response key is **`delivered`** (`gaos` | `local`), never `via`. Every 409 of the route carries a `code`: `already_answered` (existing case, now with `code`), `newer_round`, `answered_in_gaos`, `answered_here`, `in_flight`; the dialog words each.
11. **Reuse.** Round: `extRoundRe` (`learning_loop.go`). Actor: `convActor` (`conversations.go`) gives the real and effective names; display = "<real> as <target username>" when impersonating, else the full name. GAOS product id: one helper `gaosProductFor(ctx, d, pid) string` ("" unless `gaos_integrated = 1`, `ValidProductID` and `r.gaos.Configured()`), used by `case_automation.go`, `learning_loop.go` and the relay. The builds' latest approval comes from the `case_approvals` query `enrichBuilds` already runs (it reads the extra columns). Answer-source labels are `ANSWER_SOURCE_LABEL` (not `SOURCE_LABEL`). The dialog's comment allows 1000 characters.
12. **Lists.** `GET /api/history/approvals` reads `case_approvals WHERE status = 'open'` (no index on `status`; the table holds hundreds of rows — add one past ~100k), then `job_runs WHERE id IN (…)`. `title` = `payload.draft.title`; `spec_path` = `payload.spec_path`; `report` = `payload.report` (the keys `job_events.go` reads). `approval=open` on builds is `EXISTS (SELECT 1 FROM case_approvals a WHERE a.job_id COLLATE utf8mb4_general_ci = j.id COLLATE utf8mb4_general_ci AND a.status = 'open')` in the main WHERE; `HistoryView.tsx` adds `approval` to the Builds tab's keys.
13. **PR body wording.** `learnloop/draft.go`: "Disetujui di QA tools oleh: %s" becomes "Disetujui oleh: %s" (the value now says where, e.g. "ardi (QA tools, history)" or "budi (GAOS)").
